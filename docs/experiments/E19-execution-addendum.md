# E19 execution addendum — confirmation transport

The locked E19 development is running serially. To complete the 80-replicate fresh check efficiently, a separate transport can execute the already defined confirmation jobs on eight worker processes. This operational addendum is written after development began but before confirmation outcomes. It changes no candidate, seed, cohort, assignment, action, coefficient, selection rule or analysis. The serial pipeline remains preserved and usable. Worker execution order does not enter semantic randomness.

`scripts/run_e19_parallel_confirmation.py` calls the frozen engine with the exact jobs/resolved settings from `e19_teacher_studies.py`. Each worker owns a distinct raw class directory; the parent records inventory in the serial job order. Partial class outputs are retained, complete outputs require hash and identity verification, and all outputs are re-read by the unchanged E19 audit helpers. A test compares every raw table and manifest field with serial simulation and checks hash-preserving reuse. The driver, its test and this addendum are hashed together with the frozen selection before any confirmation execution. Confirmation completion also hashes this execution lock.

The same transport optionally parallelizes confirmation's per-class raw audit and metric extraction. Its `--analyze` mode calls the original hash/identity checks, raw validators and metric helpers; it merges returned parts in serial job order and uses the original weighting and paired-bootstrap functions. It preserves the exact E19 contrast list, primary-family flag and Bonferroni rule. The transport test also checks that each audited subgroup metric equals the serial helper result. The derived manifest records this execution lock. Serial development analysis is unchanged. This adds an execution route; it does not change the statistical analysis definitions.

This is a performance change only. It does not relax or override the frozen design or reinterpret failed results.
